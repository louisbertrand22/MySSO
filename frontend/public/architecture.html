MySSO · architecture technique

Architecture de MySSO

Un fournisseur d'identité OAuth 2.0 / OpenID Connect maison. Un backend Express unique émet et vérifie tous les jetons, signés en RS256 avec une clé RSA locale. Un frontend Next.js porte les écrans que l'utilisateur voit : connexion, consentement, tableau de bord et console d'administration. PostgreSQL, via Prisma, est la seule source de vérité : sessions, codes d'autorisation, consentements et journal d'audit y vivent tous.

Vue d'ensemble

Qui parle à qui

  • Un seul émetteur de jetonsSeul le backend Express signe des JWT. La clé privée ne quitte jamais keys/private.pem ; la clé publique est publiée sur /jwks.json.
  • Le frontend n'a pas de logique d'authLes pages Next.js appellent l'API avec fetch. Toute décision (mot de passe, consentement, émission de code) se prend côté Express.
  • Une base, aucune donnée en mémoireCodes d'autorisation, refresh tokens, sessions et consentements sont en base. Le serveur est sans état, à part les compteurs de rate limit.
  • Les applis clientes sont déclaréesChaque Client a une liste de redirectUris et de scopes autorisés. Une redirection hors liste est refusée avant même la connexion.
  • Les admins sont un scopeUn utilisateur isAdmin reçoit le scope admin dans son access token ; requireScope('admin') protège tout /admin/*.
  • Tout est tracéSecurityLogger écrit chaque événement sensible dans logs/security.log et dans la table AuditLog, lue par la console admin.
Flux OpenID Connect

Authorization code + PKCE, en seize étapes

Une appli cliente qui veut connecter un utilisateur l'envoie sur GET /authorize avec son client_id, une redirect_uri, un state, un nonce et un code_challenge. Le backend vérifie la redirect_uri contre la liste du client avant toute autre chose, puis cherche une session : jeton Bearer ou cookie accessToken.

Sans session, l'utilisateur passe par la page de connexion du frontend, qui le renvoie ensuite sur /authorize grâce au paramètre returnTo. Sans consentement enregistré pour ce client, il passe par la page de consentement. Le code émis vit 60 secondes et ne sert qu'une fois.

* JWT_EXPIRATION, 3600 s par défaut.

  • Rotation à chaque refresh : POST /auth/refresh vérifie la signature, le type, la présence en base, l'expiration et l'existence d'au moins une session active, puis supprime l'ancien refresh token et en émet un nouveau sur la même Session.
  • Le scope admin est recalculé au refresh à partir de User.isAdmin : retirer le droit admin prend effet au plus tard 15 minutes après.
  • Compte désactivé : authMiddleware relit isDisabled en base à chaque requête, le blocage est donc immédiat.
  • Sessions visibles : chaque connexion crée une Session avec IP et user-agent ; l'utilisateur les liste et les révoque depuis son tableau de bord (/user/sessions).
  • Déconnexion partout : POST /auth/logout avec all supprime tous les refresh tokens et pose revokedAt sur toutes les sessions.
  • Changement ou réinitialisation de mot de passe : toutes les sessions et refresh tokens de l'utilisateur sont supprimés.
Données

Onze tables, toutes autour de User

Un réglage en base, pas en variable d'environnement. L'obligation de vérifier son email avant de se connecter se lit dans SystemSetting['requireEmailVerification'], modifiable depuis /admin/settings. Sans SMTP configuré, les liens de vérification et de réinitialisation sont écrits dans la console du serveur.

Frontend

Seize pages Next.js, toutes côté client

Le dossier frontend/ est une appli Next.js 16 (App Router) indépendante, qui ne parle au backend que par NEXT_PUBLIC_API_URL. AuthContext garde l'utilisateur courant, décode l'access token pour en tirer l'identité et le rafraîchit au chargement s'il a expiré. lib/api.ts et lib/adminApi.ts regroupent les appels.
